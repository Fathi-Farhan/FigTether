## Context

Wrong-tab reads (`P06`) happen when identity is guessed from visible labels: two files can share a
name, `fileKey` is not generally available to public plugins (`S7`), and user-visible names change
freely during authoring. PRD 8.4 decides the entity model: `session_id` is a UUID per plugin run
or tab and never derives from file name or `fileKey`; `document label` is a human-facing name that
is not a routing key and can change; the file URL is only an optional hint whose mapping to a
session must be user-confirmed when the plugin cannot provide verifiable identity; two same-named
files must never map automatically; `node_id` is only meaningful together with its session or
snapshot. `FR04` limits discovery: `list_sessions` returns only sessions granted to this client,
and every read requires `session_id` or `snapshot_id`. Committed interpretation 2 (in
`docs/00-overview/01-prd-analysis.md` section 10) keeps identity fail-closed: ambiguity denies.

## Decision

1. `session_id` is a UUIDv4 generated by the plugin runtime when a plugin run or tab starts and
   connects. It lives in plugin UI memory only, per the 8.6.2 storage rule (credentials and
   session data never in client storage or local storage), and dies with the run.
2. Identity never derives from: document name, `fileKey` (`S7`), page name, URL, node names, or
   selection. None of these is a routing input for any tool, cache entry, log field of
   authorization, or resource URI.
3. Document labels are non-authoritative: they appear in the grant UI, in `list_sessions`
   summaries, and in diagnostics solely for human reading; they are never compared or used as
   keys (`P06`, 8.4 entity row).
4. URL mapping stays optional and confirm-first: when the plugin can present a verifiable
   identity tied to a session (the pairing flow of PRD 5.1), the mapping is shown for explicit
   user confirmation; without that, no URL-based routing exists. Two files with the same name are
   never auto-mapped (8.4 closing rules).
5. Related entities stay separate per 8.4: `connection_epoch` rises on every reconnect and old
   epoch answers are discarded; `daemon_instance_id` distinguishes processes across restarts;
   `grant_id` and `grant_epoch` version the authorization; `snapshot_id` binds to its originating
   session and grant with a content hash; offline bundles are always labeled
   `source.kind=offline_bundle`, never as live (`FR21`).
6. Restarts yield new identity and regrant: plugin restart, daemon restart, or a new tab creates a
   new session requiring fresh pairing and grant (8.4 state machine and 8.7 crash row). A brief
   reconnect within the same plugin run may reuse still-valid in-memory credentials but must raise
   `connection_epoch` and discard in-flight old-epoch work (`FR16`).

## Rationale

Random UUID identity removes several failure classes at once: wrong-tab reads (`P06`), the
restart confusion listed in 8.7 (stale runtime files must be detected, never trusted), and the
impossibility of routing on `fileKey` when it is hidden from plugins (`S7`). Names and URLs as
keys would let identical labels collide silently; the PRD explicitly refuses to make that hint an
authorization input. Keeping identity strictly session-scoped also matches the grant model
(ADR-004), which binds scope to a session, not to a document.

## Consequences

- Positive: routing is one mechanism across all tools; `list_sessions` can be safely grant-aware;
  restart semantics match the connection evidence (`AT09`).
- Negative: agents must carry `session_id` per call, and the optional URL hint flow needs an extra
  confirmation step; UUID churn on restart is visible in logs and support threads.
- Neutral: display names still travel in results for readability, but only as labels in
  summaries, never as identity.

## Alternatives considered

- `fileKey`-based identity: rejected; unavailable to public plugins (`S7`), and it would wrongly
  couple sessions to a document when grants are subtree-scoped to sessions.
- Document name plus creation-time heuristics: rejected; two same-named files must never map
  automatically (explicit 8.4 rule, `P06`).
- Persistent per-file session IDs across restarts: rejected; regrant after restart is a security
  feature (8.4, 8.6.1 credential rotation and 8.7 crash rules).
- One implicit session per client connection: rejected; multi-session support and per-session
  grants are P0 product structure (grant registry, session limit 4 in 8.5.5).

## Verification

Evidence: two-session test sharing node IDs with disjoint grants (no crosstalk in data, cursors,
or assets); restart tests showing a new `session_id` plus failed reuse of stale runtime files;
URL hint flow recording an explicit user confirmation before any mapping applies.
AT refs: AT05 (session isolation), AT09 (reconnect, restart, and epoch handling), AT03 (pairing
flow onboarding).
Gate: G0 (E01 pairing and session probes feeding `D05`), G1 (isolation and restart fixtures),
G2 (release evidence).
